M3LB · GPU throughput

MLUPS is not a unit of speed

A lattice Boltzmann step is bound by memory bandwidth almost everywhere, so lattice updates per second is very nearly bandwidth ÷ bytes per node. Two codes can differ by a factor of three in MLUPS while using the machine equally well. This page states what M3LB moves per node, what fraction of the card it actually gets, and which number survives a comparison with another implementation.

What the card actually does

The cubic box is the simplest configuration the code will run: a cube, a one-cell solid shell on all six faces, no forcing, no coupled fields. Three readings, each reported by box itself alongside its GB/s and its percentage of peak.

ConfigurationBGKCentral moments% of 320 GB/s
at rest, walls908.6912.361.3 / 61.6
decaying vortex, walls917.3919.961.9 / 62.1
at rest, -periodic932.4933.862.9 / 63.0

The initial state does not change the rate. At rest and stirred differ by about 1% — run-to-run noise. Every node reads 27 populations, does the same arithmetic and writes 27 back whatever the values are; there is no branch on a population and no data-dependent path in the kernel. A quiescent box and a stirred one time the same, so quoting the at-rest figure costs nothing in honesty.

Walls cost 2.6%, 932 → 909. A solid cell is skipped, and under Esoteric Pull that is halfway bounce-back: the slot a fluid node emits toward a wall belongs to the wall, which never touches it, so the node reads its own emission back reversed one step later. No-slip, second order on a grid-aligned flat wall, one byte per node, no extra kernel. The 2.6% is the templated geometry path — loading the flags unconditionally cost twice as much.

The at-rest run conserves mass trivially, so it proves throughput and nothing else. -u0 0.05 starts a divergence-free vortex that vanishes on all six wall planes, and then the mass-drift column is a real check on the same kernel at the same speed. In FP32 that drift settles at ~7e−7 and stays there — 7.252e−07, 7.240e−07, 7.240e−07 at 40, 400 and 4000 steps, and exactly zero in FP64. It is one-time quantisation of the weights onto the nearby FP32 fixed point. A leak would grow with step count.

Measured · the result worth the comparison

A 27-moment collision for free

Central moments run at 912.3 MLUPS against BGK's 908.6 — the more elaborate operator is, within noise, not slower. It should not be: the step is bandwidth-bound and both operators move the same 216 B per node. The full central-moment transform is a separable 3×3×3 product, so it costs arithmetic on registers the kernel is already waiting on memory to fill.

This is the claim the code exists to make. Galilean-invariant collision, modular physics, and the throughput of the simplest operator in the literature — not one traded against the other. It is also the number to watch when someone reports that their advanced operator costs 30%: on a bandwidth-bound step, that is a statement about their implementation, not about the scheme.

The Kokkos code in the parent directory collapses on GPU under central moments where this one does not. That is an artefact of that implementation and is still open; it is named here so the discrepancy is not discovered as a surprise.

Implied · capacity, not speed

1390³ does not fit on an H200

D3Q27 in FP32 is 27 × 4 = 108 B per node, plus one geometry byte. There is exactly one lattice — Esoteric Pull updates in place — and nothing streams from host memory or splits across devices, so capacity alone fixes the ceiling.

box computes this for whatever card it finds, prints the largest cube that fits, and skips the rest rather than dying inside cudaMalloc.

If 1390³ came from another code's table, note what it implies: 2.69 × 10⁹ nodes in 141 GB is a budget of 52 B/node. D3Q19 in FP16 is 38 B and D3Q27 in FP16 is 54 B — so that run is half-precision storage, and it is not an FP32 comparison. Worth establishing before the MLUPS figures are set beside each other, because the same fact sets both the memory ceiling and the throughput.

What should carry across

The percentage, not the MLUPS. A T4 reaches ~61% of its theoretical pin bandwidth here; if that fraction holds on an H200's 4.8 TB/s the rate follows directly. HBM parts commonly reach a higher fraction than GDDR6 on a pure streaming kernel, so the lower entry is closer to a floor than to an estimate — which is exactly what the run is for.

Expect the two grids to give nearly the same MLUPS. Past the L2 cache the rate is set by bytes per node and by the memory system, not by how many nodes there are. A sweep that climbs steeply with size is usually measuring launch overhead at the small end.

Method

Reproducing this

Verified on a Tesla T4 under CUDA 12.8. -DLBM_GPU_ARCH=90 is the Hopper build and compiles clean; FP32 is the default and is what belongs in a throughput comparison.

## build
cmake -S GPU -B GPU/build -DCMAKE_BUILD_TYPE=Release -DLBM_GPU_ARCH=90
cmake --build GPU/build -j

## the sweep: BGK and CM at 520^3 / 720^3 / 1390^3
./GPU/build/box

## one size, one operator
./GPU/build/box -n 720 -op bgk

## walls off, for codes that time an empty periodic box
./GPU/build/box -n 720 -periodic

## the stability check: a decaying vortex, same kernel, same rate
./GPU/build/box -n 256 -u0 0.05

Traffic is counted as 27 reads plus 27 writes per node per step. Esoteric Pull's advantage is footprint — one lattice in memory instead of two — not traffic, and counting it as half the bytes would flatter the result. The percentages on this page are computed against the device's theoretical pin bandwidth, read from cudaDeviceGetAttribute rather than the fields CUDA 12 deprecated.

Source: GPU/src/box.cu. The long comment at the top of that file carries the same caveats, so they travel with the code rather than only with this page.
